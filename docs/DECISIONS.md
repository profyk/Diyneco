# Decisions

Decisions the specifications did not make, or where they had to be reconciled. Newest at the
bottom. G-numbers were approved with the Phase 1 plan; D-numbers were made while building
and are open to review.

| # | Date | Decision | Reason |
|---|------|----------|--------|
| G1 | 2026-10-08 | `app.folio_balances` is created `WITH (security_invoker = true)`. | A plain view runs as its owner and would show every hotel's balances. |
| G2 | 2026-10-08 | `app.hotels` has RLS with policy `id = app.current_hotel_id()`. | It has no `hotel_id` column, so the spec's loop skipped it. |
| G3 | 2026-10-08 | `diyneco_owner` has `BYPASSRLS`; it runs migrations and owns the narrow `SECURITY DEFINER` functions only. | `FORCE ROW LEVEL SECURITY` applies to the owner too, so `redeem_pairing` could never find a row before a hotel is known. |
| G4 | 2026-10-08 | Definer functions `app.user_memberships(user_id)` (login) and `app.invitation_lookup(token_hash)` (invitation acceptance). | Both run before a hotel is selected, when RLS hides every membership and invitation. |
| G5 | 2026-10-08 | The worker drains the outbox through `app.outbox_claim`, `app.outbox_mark_published` and `app.outbox_purge`. | The worker has no `BYPASSRLS`, and the outbox spans hotels. |
| G6 | 2026-10-08 | Single-column foreign keys between tenant rows became composite `(hotel_id, id)` keys (payment allocations, tips, invoice items, order item modifiers, webhook deliveries, reversal and adjustment targets, order/payment/adjustment references on folio entries, payments, adjustments, credit notes, order status history). | G7 | 2026-10-08 | RLS is forced on every table with `hotel_id`, including `roles`, `charge_categories`, `audit_logs`, `feature_flags`. `feature_flags` is read-only for the app roles. | The migration check requires it; flags are changed by the platform only. |

| G9 | 2026-10-08 | New table `app.data_keys` (per-scope data keys wrapped by the KMS master key). `KMS_PROVIDER=local` with `KMS_LOCAL_MASTER_KEY` for development and CI; production must use a cloud KMS (refused at start-up otherwise). | G10 | 2026-10-08 | Columns `users.failed_window_start` and `hotel_users.pin_failed_window_start`. | "5 failures in 15 minutes" cannot be measured from a bare counter, and platform audit rows are unreadable by the API. |
| G11 | 2026-10-08 | An access token is bound to one hotel. Login takes an optional `hotel_id`; `/auth/refresh` takes `{hotel_id}` to switch; `X-Hotel-Id`, if sent, must equal the token's hotel or the request gets `404`. Sessions record the hotel in `sessions.active_hotel_id` (named so it is not mistaken for tenant data). | The token carries a per-hotel `perms_v`, so it cannot serve several hotels. |
| G12 | 2026-10-08 | Signup and invitation acceptance return no tokens; the user signs in afterwards. Anonymous idempotent requests use principal key `anon`. | Stored idempotent responses would otherwise keep live tokens in the database. | G13 | 2026-10-08 | An `in_progress` idempotency claim older than 60 s is treated as abandoned and retaken. 2xx and 4xx outcomes are stored and replayed; 5xx releases the key. | A crashed request would otherwise block its key for 24 hours; `SERVICE_UNAVAILABLE` is documented as safe to retry with the same key. |
| G14 | 2026-10-08 | Worker may `DELETE` from `idempotency_keys`, `sessions`, `one_time_tokens`; `app.ensure_partitions()` creates monthly partitions 3 months ahead and revokes the app roles' rights on each partition. No default partition. | Retention jobs need to delete; partitions bypass the parent's RLS if reachable directly. |
| G15 | 2026-10-08 | The ten initial schema migrations create indexes without `CONCURRENTLY`. The rule applies from the first migration after Phase 1. | `CONCURRENTLY` cannot run inside a transaction, and the tables are empty when created. |
| G16 | 2026-10-08 | Breached-password check uses a bundled list: the 12+ character entries of the NCSC top 100,000 list from SecLists (MIT), lower-cased, in `backend/app/core/data/common_passwords.txt`. | No network dependency at login; shorter entries are already rejected by the 12-character minimum. An online k-anonymity check can be added later. |
| G17 | 2026-10-08 | `invoice_prefix` at signup is the hotel name's initials (2 to 4 letters), editable in settings. | The column is required and signup does not ask for it. |
| G18 | 2026-10-08 | A request from an origin in `CORS_ALLOWED_ORIGINS` is a web client: the refresh token goes in a `__Host-diyneco_rt` cookie (`Secure`, `HttpOnly`, `SameSite=Strict`) and is omitted from the body, and the 12-hour idle limit applies. Other clients get the token in the body. | The spec says cookie on web, body on mobile, but not how the server tells them apart. |
| G19 | 2026-10-08 | `diyneco_platform` exists with no grants. How platform endpoints write (approve hotels, edit plans) is decided in Phase 7. | The spec gives the role no table access yet expects it to change tenants and plans. |
| D1 | 2026-10-08 | Plan prices are placeholders: all three plans R0/month, limits starter 50 rooms/60 devices/40 staff/2 keys, professional 250/300/150/5, enterprise 2000/2400/1000/20, marked `features.placeholder = true`. | Prices and limits are not in the specs. | D7 | 2026-10-08 | A wrong step-up password returns `403 PIN_INVALID` with `details.credential = "password"` and counts towards the login lockout. | D11 | 2026-10-08 | New event types `HOTEL_UPDATED` and `SETTINGS_UPDATED` on `hotel:{id}:ops`; `TENANT_CREATED` on `platform` at signup. | The spec lists "settings events" on the ops channel without naming them. Needs adding to the API spec's channel table. |
| D12 | 2026-10-08 | MFA is mandatory for users holding the system roles Hotel Owner, Hotel Admin, General Manager or Finance Manager (and for all platform accounts). | D13 | 2026-10-08 | Email verification is not required to sign in. | The spec does not require it. Open question for Phase 2. |

| D15 | 2026-10-08 | Card-data screening runs on every JSON request body: any value that is a 13 to 19 digit Luhn-valid number, or any field named `cvv`, `cvc`, `card_number`, `pan`, `track` and similar, returns `400 CARD_DATA_REJECTED`. | D16 | 2026-10-08 | Audit log and notification rows with `hotel_id` NULL are written without `RETURNING` (SQLAlchemy `implicit_returning=False`), and notification delivery status is set through `app.notification_mark`. | RLS lets the app roles write platform-level rows but never read them back, and `RETURNING` counts as a read. |

| D18 | 2026-10-08 | Rate limits: 10/min per IP on signup, login, MFA verify, refresh, step-up, password and email endpoints and invitation acceptance; 600/min per staff user on every authenticated request. | API spec defaults applied to the Phase 1 endpoints. |

| D20 | 2026-10-09 | Nobody can change the roles of, deactivate, or reset the PIN of a member who holds any permission they lack, and nobody can do these to themselves (`PERMISSION_DENIED`). | Extends the cannot-grant rule to removal: otherwise a General Manager could demote or lock out the Owner. |
| D21 | 2026-10-09 | A hotel always keeps at least one active Hotel Owner (`INVALID_TRANSITION`). | A hotel without an owner could never manage its subscription again. |
| D22 | 2026-10-09 | Custom roles get code `custom_<slug>_<6 hex>`; names are unique (case-insensitive) among the roles a hotel sees. Deactivating a member revokes their sessions bound to this hotel only. `PATCH /staff/{id}` may change the name only of someone who belongs to this hotel alone. | Roles have no description column; one user account can serve several hotels (G11). |
| D23 | 2026-10-09 | Device credentials: new `POST /devices/token` exchanges the credential for a 1-hour device token (claims `sub`, `kind=device`, `dk`, `hid`, `rid`); lookup through the definer function `app.device_lookup` (migration 0011, with a unique index on `credential_hash`). | D24 | 2026-10-09 | Device lock, unlock, reset, disable, reassign and unpair take an `Idempotency-Key`. `unlock` returns a locked or disabled device to active. | D25 | 2026-10-09 | Onboarding steps are derived from data: account = an owner's email is verified; hotel profile = phone and address set; settings and room charging = saved at least once (an audit entry `settings.update` or, when nothing changed, `settings.reviewed`); devices = a kitchen display paired; tablet pairing = a guest tablet paired; staff invites = an invitation sent or a second member. | The spec lists the steps but not when each is done; the settings defaults are valid values, so "done" means reviewed. |
| D26 | 2026-10-09 | Plan limits count rooms not deleted, devices not revoked, and staff as active members plus pending invitations. Device limits are checked when a pairing code is issued and again when it is redeemed. | An accepted invitation must never break a limit. |

| D40 | 2026-10-09 | Kitchen display: `POST /auth/kitchen/sign-in` takes `{user_id, pin}` and `GET /kitchen/staff` (display token) lists names for the picker. A kitchen session lasts 8 hours without refresh, carries `kitchen.*` permissions only, is bound to its display (ends if the display is disabled or unpaired) and is ended by the next sign-in on that display. The display token alone can read the board. Any station with items on an order can accept the whole order; `start` moves the order to PREPARING and the caller's own items. Undo (`unready`) works within 2 minutes and only while the order is still PREPARING, because the lifecycle has no READY→PREPARING. Extra events: `ORDER_UPDATED` on kitchen channels, `ORDER_ITEM_READY` on the room and ops channels. | The spec says "staff PIN on a kitchen display" but not how the person is identified (PINs are not unique). |

| D41 | 2026-10-09 | Room service and payments: a payment for an order needs the caller to be its assignee unless they hold `deliveries.manage`; a payment against a whole bill (`stay_id`) also needs `folio.read`. The payment's folio entry covers at most the amount due; the tip is a separate entry credited to the person who recorded it. Late entries need `occurred_at` with a time zone, at most 72 hours back, and a reason when older than 10 minutes. Managers may reassign an assigned delivery to anyone holding `deliveries.update`. Extra ops event `ORDER_CLOSED`. | The spec's hard limit says room-service staff pay only for their own orders; the rest fills gaps the payment rules leave. |
| D42 | 2026-10-10 | Folio: `POST /folios/{id}/charges` takes any revenue category except accommodation; tip and payment categories are refused. A discount is split across the chosen revenue groups in proportion to their charges, posted to `accommodation`, `food` or `other_services` with VAT at the hotel rate; a percent that rounds to zero is refused. An adjustment starts from the current amount (the charge plus its reversals and approved adjustments); approval is refused if that amount changed after the request; the correcting entry uses the target's category and VAT rate (for an order, the category of its first charge). | The spec names the operations but not how amounts are split or how concurrent adjustments behave. |
| D43 | 2026-10-10 | (User decision.) A company stay uses the request address if given, otherwise the billing profile's. | D44 | 2026-10-10 | (User decision.) A credit note cancels a whole invoice: reason, `invoices.credit` and step-up; only while the folio is closed and only once per invoice. | D45 | 2026-10-10 | Checkout: any order not CLOSED, CANCELLED or DECLINED blocks it (`OPEN_ORDERS`, never overridable); the override covers the balance only (`OVERRIDE_NOT_ALLOWED` if the hotel forbids it, `PERMISSION_DENIED` without `checkout.override`, `REASON_REQUIRED` without a reason); a credit balance is allowed. The database refuses entries on a closed folio, so an overridden balance cannot be paid against the bill; it waits for the accounts-receivable list (Phase 8). | Fills the gaps in the checkout rules; the security spec asks the hotel to confirm long-stay VAT treatment. |
| D46 | 2026-10-10 | Bills are rendered server-side with fpdf2 (pure Python, PDF core fonts, Latin-1 text) and stored in the private `invoices` bucket at `hotels/{hotel_id}/invoices/{invoice_id}.pdf` before the invoice row is written (invoices are append-only); the SHA-256 is kept on the row. `GET /invoices/{id}/pdf` returns a 5-minute signed URL and is audited. | D47 | 2026-10-10 | Stay changes: `PATCH /stays/{id}` (If-Match; `GET /stays/{id}` now returns an ETag) moves both dates of a reservation; a checked-in stay keeps its arrival, departure may not be before today, added nights are posted at the stay's rate with today's VAT settings, and removed nights (dated on or after the new departure) are reversed; refused if a removed night has a pending or approved adjustment. `POST /stays/{id}/move` (step-up, optional reason) keeps the nightly rate; for a checked-in guest the target must be ready and free for the remaining nights, open orders block the move (`OPEN_ORDERS`, they carry the old room number), the old room goes to `room_status_after_checkout`, its tablet resets, and `STAY_CHECKED_IN` goes to the new room plus an extra ops event `STAY_MOVED`. | The spec gives the outcome but not the rules around rates, past nights and open orders. |

Admin routes under `/admin` may name a hotel in the path (route check exemption). New table `support_grants` (tenant RLS): a grant needs `platform.support`, step-up and a ticket reference, lasts at most 60 minutes, emails the hotel's owners, is listed at `GET /support-access` (`audit.read`) and revocable at `POST /support-access/{id}/revoke` (`hotel.update`). It returns a token of kind `support` valid until the grant ends: GET only, permissions limited to `hotel.read, settings.read, rooms.read, devices.read, staff.read, menu.read, kitchen.view, orders.read, deliveries.view, payments.read, reports.read, subscription.read` (nothing that returns guest data). A subscription's `limit_overrides` now take precedence over the plan's limits. Extra platform events `TENANT_APPROVED`, `TENANT_REACTIVATED`; owners are emailed on approval. | The spec gives `diyneco_platform` no table access yet expects tenant and plan changes, and defines support access without a table. |
| D49 | 2026-10-10 | The `platform` realtime channel is served by the same gateway for platform tokens with MFA. | D50 | 2026-10-10 | API keys (`X-Api-Key`) work on any endpoint whose permission the key holds. Audit entries carry `actor_type = 'api_key'` and the key id. | The spec makes `api_key` a principal kind but lists no endpoint for it. |

While suspended and `read_only_when_suspended`, the hotel's staff and API keys are read-only except `/subscription` and `/auth` (new error code `SUBSCRIPTION_SUSPENDED`, 403; proposed for the API spec), like a platform suspension; guest devices are not affected, and nothing is deleted. Plan-free trials may now end as expired or cancelled without a plan. **Emails** (subscription confirmed, renewal coming, trial ending and ended, payment received and failed, reminder, overdue, upgrade, scheduled change, cancelled, suspended, reactivated, refund; invoices and credit notes as before) go to the billing contact or the owners through the mailer (every attempt logged; a failed email never repeats a payment) with a `BILLING_NOTICE` event on the ops channel; links go to the signed-in Merchant app. **Dashboard** (`/admin/billing/summary|invoices|payments|webhooks|provider`, billing managers): collected (received less refunds, test excluded), invoiced (less credit notes), outstanding and overdue, MRR/ARR from agreed prices (`admin_mrr` now uses subscription snapshots), counts and revenue by plan, per currency and never mixed; invoice and payment lists with search, filters, paging and CSV export (5,000 rows, formula-safe cells); reconciliation marks. Collections settings (reminders, grace, lead days, suspension, read-only, proration, provider, EFT) are edited in Admin > Billing & Invoices. | Owner's brief sections 5, 6 and 9-12; Stitch replaces PayFast (D73); restrictive choices where the brief left policy open. |

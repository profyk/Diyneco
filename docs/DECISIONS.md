# Decisions

Decisions the specifications did not make, or where they had to be reconciled. Newest at the
bottom. G-numbers were approved with the Phase 1 plan; D-numbers were made while building
and are open to review.

| # | Date | Decision | Reason |
|---|------|----------|--------|
| G1 | 2026-10-08 | `app.folio_balances` is created `WITH (security_invoker = true)`. | A plain view runs as its owner and would show every hotel's balances. |
| G2 | 2026-10-08 | `app.hotels` has RLS with policy `id = app.current_hotel_id()`. | It has no `hotel_id` column, so the spec's loop skipped it. |
| G3 | 2026-10-08 | `diyneco_owner` has `BYPASSRLS`; it runs migrations and owns the narrow `SECURITY DEFINER` functions only. | `FORCE ROW LEVEL SECURITY` applies to the owner too, so `redeem_pairing` could never find a row before a hotel is known. |
| G4 | 2026-10-08 | Definer functions `app.user_memberships(user_id)` (login) and `app.invitation_lookup(token_hash)` (invitation acceptance). | Both run before a hotel is selected, when RLS hides every membership and invitation. |
| G5 | 2026-10-08 | The worker drains the outbox through `app.outbox_claim`, `app.outbox_mark_published` and `app.outbox_purge`. | The worker has no `BYPASSRLS`, and the outbox spans hotels. |
| G6 | 2026-10-08 | Single-column foreign keys between tenant rows became composite `(hotel_id, id)` keys (payment allocations, tips, invoice items, order item modifiers, webhook deliveries, reversal and adjustment targets, order/payment/adjustment references on folio entries, payments, adjustments, credit notes, order status history). References to tables that mix system and hotel rows (`user_roles.role_id`, `folio_entries.category_id`) use trigger `app.check_shared_ref`. `role_permissions` follows its role's visibility through RLS and can only be changed for the current hotel's own roles. | RLS checks only the new row, not the row it points to; without this a row in hotel A could reference hotel B. |
| G7 | 2026-10-08 | RLS is forced on every table with `hotel_id`, including `roles`, `charge_categories`, `audit_logs`, `feature_flags`. `feature_flags` is read-only for the app roles. | The migration check requires it; flags are changed by the platform only. |
| G8 | 2026-10-08 | New table `app.mfa_recovery_codes` (10 hashed, single-use codes per user). | The security spec requires recovery codes but the schema had nowhere to store them. |
| G9 | 2026-10-08 | New table `app.data_keys` (per-scope data keys wrapped by the KMS master key). `KMS_PROVIDER=local` with `KMS_LOCAL_MASTER_KEY` for development and CI; production must use a cloud KMS (refused at start-up otherwise). These two variables are additions to the runbook's `.env.example`. | Envelope encryption needs somewhere to keep wrapped keys and a key source for development. |
| G10 | 2026-10-08 | Columns `users.failed_window_start` and `hotel_users.pin_failed_window_start`. | "5 failures in 15 minutes" cannot be measured from a bare counter, and platform audit rows are unreadable by the API. |
| G11 | 2026-10-08 | An access token is bound to one hotel. Login takes an optional `hotel_id`; `/auth/refresh` takes `{hotel_id}` to switch; `X-Hotel-Id`, if sent, must equal the token's hotel or the request gets `404`. Sessions record the hotel in `sessions.active_hotel_id` (named so it is not mistaken for tenant data). | The token carries a per-hotel `perms_v`, so it cannot serve several hotels. |
| G12 | 2026-10-08 | Signup and invitation acceptance return no tokens; the user signs in afterwards. Anonymous idempotent requests use principal key `anon`. | Stored idempotent responses would otherwise keep live tokens in the database. Device pairing (Phase 3) needs the same treatment for its one-time credential. |
| G13 | 2026-10-08 | An `in_progress` idempotency claim older than 60 s is treated as abandoned and retaken. 2xx and 4xx outcomes are stored and replayed; 5xx releases the key. | A crashed request would otherwise block its key for 24 hours; `SERVICE_UNAVAILABLE` is documented as safe to retry with the same key. |
| G14 | 2026-10-08 | Worker may `DELETE` from `idempotency_keys`, `sessions`, `one_time_tokens`; `app.ensure_partitions()` creates monthly partitions 3 months ahead and revokes the app roles' rights on each partition. No default partition. | Retention jobs need to delete; partitions bypass the parent's RLS if reachable directly. |
| G15 | 2026-10-08 | The ten initial schema migrations create indexes without `CONCURRENTLY`. The rule applies from the first migration after Phase 1. | `CONCURRENTLY` cannot run inside a transaction, and the tables are empty when created. |
| G16 | 2026-10-08 | Breached-password check uses a bundled list: the 12+ character entries of the NCSC top 100,000 list from SecLists (MIT), lower-cased, in `backend/app/core/data/common_passwords.txt`. | No network dependency at login; shorter entries are already rejected by the 12-character minimum. An online k-anonymity check can be added later. |
| G17 | 2026-10-08 | `invoice_prefix` at signup is the hotel name's initials (2 to 4 letters), editable in settings. | The column is required and signup does not ask for it. |
| G18 | 2026-10-08 | A request from an origin in `CORS_ALLOWED_ORIGINS` is a web client: the refresh token goes in a `__Host-diyneco_rt` cookie (`Secure`, `HttpOnly`, `SameSite=Strict`) and is omitted from the body, and the 12-hour idle limit applies. Other clients get the token in the body. | The spec says cookie on web, body on mobile, but not how the server tells them apart. |
| G19 | 2026-10-08 | `diyneco_platform` exists with no grants. How platform endpoints write (approve hotels, edit plans) is decided in Phase 7. | The spec gives the role no table access yet expects it to change tenants and plans. |
| D1 | 2026-10-08 | Plan prices are placeholders: all three plans R0/month, limits starter 50 rooms/60 devices/40 staff/2 keys, professional 250/300/150/5, enterprise 2000/2400/1000/20, marked `features.placeholder = true`. | Prices and limits are not in the specs. Approved by Profy as placeholders. |
| D2 | 2026-10-08 | Local development runs PostgreSQL 17 natively; Docker Compose is provided but optional. Extensions live in schema `extensions` (Supabase's convention) and the app roles' `search_path` is `app, extensions`. | The development laptop cannot run Docker. Postgres 17 matches current Supabase. |
| D3 | 2026-10-08 | Redis is optional in development (in-process rate-limit counters) and required in staging and production (start-up fails without `REDIS_URL`). | Approved by Profy. Per-process counters do not work across several API instances. |
| D4 | 2026-10-08 | Hosting: backend on AWS or Railway (to be confirmed), web apps on Vercel, mobile apps through Expo EAS. The backend ships as one container image for API and worker; CI builds, scans and pushes it to GHCR. Deploy workflows wait for the final provider. | Stated by Profy during Phase 1. |
| D5 | 2026-10-08 | The container trusts `X-Forwarded-For` only from `FORWARDED_ALLOW_IPS` (default `127.0.0.1`), set per environment to the load balancer's range. | Trusting any proxy lets clients spoof their IP and evade per-IP rate limits. |
| D6 | 2026-10-08 | `PATCH` without `If-Match` returns `412 PRECONDITION_FAILED`. | The spec requires `If-Match` but its error catalogue has no `428`; codes must come from the catalogue. |
| D7 | 2026-10-08 | A wrong step-up password returns `403 PIN_INVALID` with `details.credential = "password"` and counts towards the login lockout. A wrong MFA code returns `401 UNAUTHENTICATED` with `details.reason = "invalid_code"` and also counts towards the login lockout. | The catalogue has no code for either case; counting them stops guessing through these endpoints. |
| D8 | 2026-10-08 | Signup with an email that already has an account creates nothing, emails that account's owner, and returns the same `201` body as a real signup. | Avoids revealing which emails have accounts. |
| D9 | 2026-10-08 | Login and forgot-password accept any email string up to 320 characters (lookup only); signup and invitations validate email syntax. | Strict validation rejects reserved demo domains such as `grandexample.example` used by the dev seed and the spec. |
| D10 | 2026-10-08 | The hotel currency cannot be changed through `PATCH /hotel/settings`; money fields must use the hotel currency (`AMOUNT_INVALID` otherwise). | Multi-currency hotels are out of scope for v1, and changing currency would corrupt existing amounts. |
| D11 | 2026-10-08 | New event types `HOTEL_UPDATED` and `SETTINGS_UPDATED` on `hotel:{id}:ops`; `TENANT_CREATED` on `platform` at signup. | The spec lists "settings events" on the ops channel without naming them. Needs adding to the API spec's channel table. |
| D12 | 2026-10-08 | MFA is mandatory for users holding the system roles Hotel Owner, Hotel Admin, General Manager or Finance Manager (and for all platform accounts). Such users get an `mfa_pending` session at sign-in that can only enrol, confirm or sign out. | Security spec MFA policy. Open question: should custom roles copied from those roles also require MFA? |
| D13 | 2026-10-08 | Email verification is not required to sign in. | The spec does not require it. Open question for Phase 2. |
| D14 | 2026-10-08 | Unknown routes and wrong methods return `404 NOT_FOUND` in the standard envelope. | The catalogue has no `405`; the envelope must always be used. |
| D15 | 2026-10-08 | Card-data screening runs on every JSON request body: any value that is a 13 to 19 digit Luhn-valid number, or any field named `cvv`, `cvc`, `card_number`, `pan`, `track` and similar, returns `400 CARD_DATA_REJECTED`. The PIN fields of staff step-up are not card PINs and are allowed. | PCI scope section; screening everywhere is simpler and stricter than per endpoint. |
| D16 | 2026-10-08 | Audit log and notification rows with `hotel_id` NULL are written without `RETURNING` (SQLAlchemy `implicit_returning=False`), and notification delivery status is set through `app.notification_mark`. | RLS lets the app roles write platform-level rows but never read them back, and `RETURNING` counts as a read. |
| D17 | 2026-10-08 | Emails are logged in `app.notifications` inside the request's transaction and sent only after commit. | A failed request must not send mail. |
| D18 | 2026-10-08 | Rate limits: 10/min per IP on signup, login, MFA verify, refresh, step-up, password and email endpoints and invitation acceptance; 600/min per staff user on every authenticated request. | API spec defaults applied to the Phase 1 endpoints. |
| D19 | 2026-10-09 | Every endpoint gated by a sensitive (†) permission needs step-up, including `POST`/`DELETE /staff/invitations` and `PATCH /staff/{id}`, which the API table leaves unmarked. | Security spec: "Permissions marked † are sensitive and always need step-up"; the more restrictive reading. |
| D20 | 2026-10-09 | Nobody can change the roles of, deactivate, or reset the PIN of a member who holds any permission they lack, and nobody can do these to themselves (`PERMISSION_DENIED`). | Extends the cannot-grant rule to removal: otherwise a General Manager could demote or lock out the Owner. |
| D21 | 2026-10-09 | A hotel always keeps at least one active Hotel Owner (`INVALID_TRANSITION`). | A hotel without an owner could never manage its subscription again. |
| D22 | 2026-10-09 | Custom roles get code `custom_<slug>_<6 hex>`; names are unique (case-insensitive) among the roles a hotel sees. Changing a custom role's permissions bumps `perms_v` for everyone holding it. Deactivating a member revokes their sessions bound to this hotel only. `PATCH /staff/{id}` may change the name only of someone who belongs to this hotel alone. | Roles have no description column; one user account can serve several hotels (G11). |
| D23 | 2026-10-09 | Device credentials: new `POST /devices/token` exchanges the credential for a 1-hour device token (claims `sub`, `kind=device`, `dk`, `hid`, `rid`); lookup through the definer function `app.device_lookup` (migration 0011, with a unique index on `credential_hash`). A replayed `POST /devices/pair` returns the stored response with `device_credential: null`. `POST /devices/heartbeat` accepts `completed_commands: ["RESET"]` to clear `reset_required`. | The security spec requires the exchange but the API spec lists no endpoint; a stored idempotent response must not keep a live secret (G12). **The API spec should list `/devices/token`.** |
| D24 | 2026-10-09 | Device lock, unlock, reset, disable, reassign and unpair take an `Idempotency-Key`. `unlock` returns a locked or disabled device to active. Reassign sets `reset_required` and sends `RESET_ROOM_SESSION` to the old room. Labels: `DY-<room>-NN`, `KITCHEN-NN`. New ops-channel events `DEVICE_PAIRED`, `DEVICE_DISABLED`, `DEVICE_REASSIGNED`, `DEVICE_REVOKED`. | CLAUDE.md: every state-changing device operation is idempotent. The spec has no separate enable endpoint. |
| D25 | 2026-10-09 | Onboarding steps are derived from data: account = an owner's email is verified; hotel profile = phone and address set; settings and room charging = saved at least once (an audit entry `settings.update` or, when nothing changed, `settings.reviewed`); devices = a kitchen display paired; tablet pairing = a guest tablet paired; staff invites = an invitation sent or a second member. | The spec lists the steps but not when each is done; the settings defaults are valid values, so "done" means reviewed. |
| D26 | 2026-10-09 | Plan limits count rooms not deleted, devices not revoked, and staff as active members plus pending invitations. Device limits are checked when a pairing code is issued and again when it is redeemed. | An accepted invitation must never break a limit. |
| D27 | 2026-10-09 | Storage: Supabase Storage in staging and production; in development a `LocalStorage` writes to `backend/.storage` and serves 5-minute signed `/dev-storage` URLs signed with the API's EdDSA keys (never mounted outside development). `POST /hotel/logo` takes `{content_type, size_bytes}` and points the hotel at the new key straight away. The `hotel-assets` bucket must be configured with a 2 MB limit and PNG/JPEG/SVG types, because Supabase's signed upload URLs do not enforce them. `httpx` became a runtime dependency. | No Supabase on the development laptop; the API spec does not say how the upload is confirmed. |
| D28 | 2026-10-09 | Additions: `GET /rooms/{id}` and `GET /devices/{id}` (for ETags); room lists sort in natural number order; ranges take an optional `prefix`; CSV rates may start with `R`. Deleting a room with any stay history is `INVALID_TRANSITION` (spec: "rejected"), and so is deleting a room with a paired tablet. | Clients need the current ETag before a PATCH; a deleted room would strand its tablet. |
| D29 | 2026-10-09 | Wrong pairing codes are counted per IP; after 5 in 15 minutes `/devices/pair` returns `RATE_LIMITED` from that IP. | Security spec: lockout after 5 failures per device or IP. A device has no identity before pairing, so IP is the key. |
| D30 | 2026-10-09 | Kitchen displays can be paired to existing stations now; station management endpoints arrive with Phase 4. | Device registry is Phase 2; stations belong to the kitchen phase. |
| D31 | 2026-10-09 | `DELETE /kitchen-stations/{id}` deactivates the station (refused while live menu items point at it); the row stays because orders and devices reference it. A modifier option with a price above zero needs `menu.price.update`. | The app roles have no DELETE on stations, and order history must keep its station. |
| D32 | 2026-10-09 | Menu item images are stored as uploaded (JPEG/WebP, 5 MB); the three resized versions are not generated yet. | Needs an image-processing job; listed under known gaps. |
| D33 | 2026-10-09 | Check-in moves a stay straight to `active` (`checked_in` is unused), needs the room `available` or `reserved`, and arrival on or before the hotel's local date with departure after it. Stays are at most 90 nights; reservations may not overlap. Every night is posted at check-in as its own entry dated that night, VAT added or contained per `accommodation_rates_include_vat`, rounded half up per night. Guest personal data is kept out of audit values. ID numbers are not accepted yet. | The spec gives the outcome of check-in but not these limits. |
| D34 | 2026-10-09 | Pricing: when menu prices exclude VAT, VAT is added per unit so guests see inclusive prices; VAT contained in each line and in the fee is rounded half up per line. Orders whose total is above the auto-approve limit (not equal to it) need approval. Modifier group min/max are enforced; sold-out items are hidden from the guest menu. | Matches the API spec's worked example (R46.96 VAT on R360). |
| D35 | 2026-10-09 | A hotel still `pending_approval` cannot take orders from tablets or staff: `422 ROOM_CHARGE_DISABLED` with `details.reason = "hotel_pending_approval"`. | API spec: a pending hotel's tablets cannot take orders; the catalogue has no closer code. |
| D36 | 2026-10-09 | Order charges post to the folio when an order becomes `NEW` (at placement or approval), whatever the payment method; cancelling posts reversing entries; declining posts nothing. Decline and cancel need a reason (`REASON_REQUIRED`). The first status-history row is written by the service; later ones by the trigger. | Payments (Phase 5) settle against folio charges. |
| D37 | 2026-10-09 | Guest tablet: orders are `room_charge` only; `/guest/session` and `/guest/info` also answer while the device is locked; the session never includes the guest's name; information pages return an empty list until a pages feature exists. | Shared screen; the paused screen still needs the hotel name. |
| D38 | 2026-10-09 | The WebSocket gateway polls `event_outbox` every 0.5 s per hotel with subscribers and fans out; replay covers 24 hours; access is re-checked every 30 s; keepalive uses `{"op":"ping"}`/`{"op":"pong"}`; the server acknowledges a subscribe with `{"op":"subscribed","seq":N}`. The 5-connection limit is per API process until Redis is in place; the `platform` channel arrives with the admin panel (Phase 7). | Works without Redis on the development laptop and needs no extra infrastructure; the outbox is already the source of truth. |
| D39 | 2026-10-09 | Error `details` are JSON-encoded (UUIDs become strings); `client_ip` returns only valid IP addresses. Ledger amounts and balances in responses use a signed money type. | Found while testing: a PRICE_CHANGED quote could not be stored for replay, and reversals are negative. |
| D40 | 2026-10-09 | Kitchen display: `POST /auth/kitchen/sign-in` takes `{user_id, pin}` and `GET /kitchen/staff` (display token) lists names for the picker. A kitchen session lasts 8 hours without refresh, carries `kitchen.*` permissions only, is bound to its display (ends if the display is disabled or unpaired) and is ended by the next sign-in on that display. The display token alone can read the board. Any station with items on an order can accept the whole order; `start` moves the order to PREPARING and the caller's own items. Undo (`unready`) works within 2 minutes and only while the order is still PREPARING, because the lifecycle has no READY→PREPARING. Extra events: `ORDER_UPDATED` on kitchen channels, `ORDER_ITEM_READY` on the room and ops channels. | The spec says "staff PIN on a kitchen display" but not how the person is identified (PINs are not unique). |

| D41 | 2026-10-09 | Room service and payments: a payment for an order needs the caller to be its assignee unless they hold `deliveries.manage`; a payment against a whole bill (`stay_id`) also needs `folio.read`. An order can be paid once it is PICKED_UP or DELIVERED, and payment (full or partial) closes it. `POST /payments` takes `card_terminal`, `cash` or `eft`; `room_charge` is not a payment (use leave-on-room), and `gateway` waits for online payments. The payment's folio entry covers at most the amount due; the tip is a separate entry credited to the person who recorded it. Late entries need `occurred_at` with a time zone, at most 72 hours back, and a reason when older than 10 minutes. Managers may reassign an assigned delivery to anyone holding `deliveries.update`. Extra ops event `ORDER_CLOSED`. | The spec's hard limit says room-service staff pay only for their own orders; the rest fills gaps the payment rules leave. |
| D42 | 2026-10-10 | Folio: `POST /folios/{id}/charges` takes any revenue category except accommodation; tip and payment categories are refused. A discount is split across the chosen revenue groups in proportion to their charges, posted to `accommodation`, `food` or `other_services` with VAT at the hotel rate; a percent that rounds to zero is refused. An adjustment starts from the current amount (the charge plus its reversals and approved adjustments); approval is refused if that amount changed after the request; the correcting entry uses the target's category and VAT rate (for an order, the category of its first charge). | The spec names the operations but not how amounts are split or how concurrent adjustments behave. |
| D43 | 2026-10-10 | (User decision.) A full tax invoice for a personal stay takes the recipient address from the checkout request (`recipient_address`); it is copied into the invoice only, not stored on the guest. A company stay uses the request address if given, otherwise the billing profile's. Without an address line, checkout returns `VALIDATION_FAILED` with `details.reason = "recipient_address_required"`. | The schema has no guest address; keeping it on the invoice only stores less personal data. |
| D44 | 2026-10-10 | (User decision.) A credit note cancels a whole invoice: reason, `invoices.credit` and step-up; only while the folio is closed and only once per invoice. It carries the negated lines and totals and shares the invoice number sequence. The folio then re-opens (the stay stays `checked_out`) so charges, discounts and adjustments can correct it, and `POST /stays/{id}/checkout` issues a new invoice without touching the room or tablet. | Issued invoices are never edited; full credit and re-issue keeps the folio and reports reconciled. |
| D45 | 2026-10-10 | Checkout: any order not CLOSED, CANCELLED or DECLINED blocks it (`OPEN_ORDERS`, never overridable); the override covers the balance only (`OVERRIDE_NOT_ALLOWED` if the hotel forbids it, `PERMISSION_DENIED` without `checkout.override`, `REASON_REQUIRED` without a reason); a credit balance is allowed. The room goes to `room_status_after_checkout`; an active tablet goes to `reset_required` (a locked one stays locked) and `RESET_ROOM_SESSION` is sent to the room channel. Stays over 28 nights need `confirm_long_stay_vat: true`. The invoice kind uses the charges total after discounts, excluding tips; numbers are `{prefix}-{hotel-local year}-{000001}`. Reversed charges and their reversals are left off the invoice lines. Emailing the bill defaults to the company's billing email or the guest's email. Added `GET /stays/{id}/invoices` (`invoices.read`). The database refuses entries on a closed folio, so an overridden balance cannot be paid against the bill; it waits for the accounts-receivable list (Phase 8). | Fills the gaps in the checkout rules; the security spec asks the hotel to confirm long-stay VAT treatment. |
| D46 | 2026-10-10 | Bills are rendered server-side with fpdf2 (pure Python, PDF core fonts, Latin-1 text) and stored in the private `invoices` bucket at `hotels/{hotel_id}/invoices/{invoice_id}.pdf` before the invoice row is written (invoices are append-only); the SHA-256 is kept on the row. `GET /invoices/{id}/pdf` returns a 5-minute signed URL and is audited. Emails attach the PDF. | No native build dependencies on the deployment image or this laptop. |
| D47 | 2026-10-10 | Stay changes: `PATCH /stays/{id}` (If-Match; `GET /stays/{id}` now returns an ETag) moves both dates of a reservation; a checked-in stay keeps its arrival, departure may not be before today, added nights are posted at the stay's rate with today's VAT settings, and removed nights (dated on or after the new departure) are reversed; refused if a removed night has a pending or approved adjustment. `POST /stays/{id}/move` (step-up, optional reason) keeps the nightly rate; for a checked-in guest the target must be ready and free for the remaining nights, open orders block the move (`OPEN_ORDERS`, they carry the old room number), the old room goes to `room_status_after_checkout`, its tablet resets, and `STAY_CHECKED_IN` goes to the new room plus an extra ops event `STAY_MOVED`. | The spec gives the outcome but not the rules around rates, past nights and open orders. |
| D48 | 2026-10-10 | Platform admin (resolves G19). Platform requests run with no hotel context, so RLS hides every tenant row from them; cross-hotel reads come only from `SECURITY DEFINER` functions owned by `diyneco_owner` (`app.admin_hotels`, `admin_metrics`, `admin_outbox_health`, `admin_flags`, `admin_platform_events`) that return aggregates and ids, never guest fields. Plans and feature flags are written through `app.admin_create_plan` and `app.admin_set_flag` (the app roles keep no write grant). Approve, suspend, reactivate, subscription changes and support grants run under the target hotel's context and are audited in that hotel's log with `actor_type = 'platform'`. The functions are granted to `diyneco_api` (the API still connects as one role); `diyneco_platform` also receives them for a future separate connection. Admin routes under `/admin` may name a hotel in the path (route check exemption). New table `support_grants` (tenant RLS): a grant needs `platform.support`, step-up and a ticket reference, lasts at most 60 minutes, emails the hotel's owners, is listed at `GET /support-access` (`audit.read`) and revocable at `POST /support-access/{id}/revoke` (`hotel.update`). It returns a token of kind `support` valid until the grant ends: GET only, permissions limited to `hotel.read, settings.read, rooms.read, devices.read, staff.read, menu.read, kitchen.view, orders.read, deliveries.view, payments.read, reports.read, subscription.read` (nothing that returns guest data). A subscription's `limit_overrides` now take precedence over the plan's limits. Extra platform events `TENANT_APPROVED`, `TENANT_REACTIVATED`; owners are emailed on approval. | The spec gives `diyneco_platform` no table access yet expects tenant and plan changes, and defines support access without a table. |
| D49 | 2026-10-10 | The `platform` realtime channel is served by the same gateway for platform tokens with MFA. Its events keep their hotel's `seq` and add `hotel_id`; clients dedupe by `event_id`; `since_seq` is ignored (no replay): the admin panel refetches when it (re)subscribes. `HEALTH_DEGRADED` is not emitted yet (it needs the monitoring job, Phase 9). | Per-hotel sequence numbers cannot order a cross-hotel stream. |

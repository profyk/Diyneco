  Purpose and scope
  Diyneco is one hotel platform with one source of truth and five specialised interfaces:
  Guest, Kitchen, Room Service, Merchant and Admin. This document fixes the
  architecture, structure, data model, compliance posture and phase plan before
  production code is written. It follows the 82-section build spec and is the reference every
  phase is checked against.

  In scope for v1: tenancy, devices, rooms, stays and folios, menu and ordering, kitchen
  stations, delivery, charge-to-room and card-at-door payments, tips, checkout with tablet
  reset, PDF bills, corporate billing, RBAC, audit, reports and the platform admin. Out of
  scope for v1: online payment gateways, PMS/POS integrations, push/SMS/WhatsApp,
  CSV/PDF report export. These are designed for, not built.

  System architecture




  Diyneco system architecture · 5 clients, 1 API, 3 stores

  All five interfaces talk only to the FastAPI backend over HTTPS and an authenticated
  WebSocket. Only the API holds database and storage credentials, so tenant isolation and
  every financial rule are enforced in one place.


  Monorepo structure
  One repository, pnpm workspaces for the TypeScript apps and a separate Python
  package for the backend. Shared API types are generated from the FastAPI OpenAPI
  schema so frontends cannot drift from the backend.

  Database schema
  All primary keys are UUIDv7 (time-ordered). Every hotel-owned table carries hotel_id
  UUID NOT NULL REFERENCES hotels and a composite index starting with hotel_id .
  Financial tables use ON DELETE RESTRICT and soft deletion ( deleted_at ) where
  deletion is allowed at all.

  Money, billing and folio model
  Every charge and payment for a stay is a row on one folio, and the folio balance is the
  single number checkout trusts. Amounts are integers in cents: R3,000.00 is stored as
   300000 .

  Folio entry types: charge (positive, has a category), payment (negative), reversal
  (mirrors a prior entry), adjustment (requires approval record). Balance = sum of charges
  − sum of payments, tips excluded from both sides.

  Tip rule (server-side only):

     \text{tip} = \max(0,\ \text{amount received} - \text{amount due})


  If received is greater than due, the API returns a pending tip and requires an explicit
  confirm call; staff cannot type a tip amount directly. If received is less than due, the
  payment is partial and the remainder stays on the folio. Worked example from the spec:
  due R3,000, received R4,000, tip R1,000; hotel revenue stays R3,000.

  Order financial lock: once the kitchen accepts an order, its line totals are frozen. Any
  change goes through adjustments with original amount, new amount, reason, requester,
  approver, timestamps and an audit entry.

  Room-charge authorisation: the service checks device→room→active stay, hotel allows
  room charging, stay not blocked, and the hotel's limit rule (e.g. auto-approve under R500,
  manager approval above). Orders over the limit sit in pending_approval and do not reach
  the kitchen.

  Checkout: blocked if balance ≠ 0 unless a manager with checkout.override re-
  authenticates and gives a reason. Checkout closes the stay, finalises the folio, issues the
  bill, publishes RESET_ROOM_SESSION , and sets the room to Cleaning.


  Security, tenancy and devices
  Tenant isolation is enforced four times: principal-bound hotel_id , repository filters,
  Postgres RLS, and automated cross-tenant tests that must fail closed.

       Principals: staff user (JWT access 15 min + rotating refresh 30 days, revocable
       sessions), guest device (long-lived device credential, SHA-256-hashed on the server,
       held in Android Keystore via SecureStore), kitchen device (device credential + staff
       PIN per action session), API key (hashed, shown once), platform admin (password +
       TOTP MFA mandatory).
       Permissions, not just roles: permission strings such as orders.read ,
        kitchen.update , folio.adjust.request , folio.adjust.approve ,
        checkout.perform , checkout.override , menu.price.update . The 10 hotel + 2 platform roles are
       seeded bundles; hotels can edit bundles within limits.
       Step-up auth: checkout, adjustments, discounts, refunds, device reset and permission
       changes require a fresh PIN or password within 5 minutes.
       Device binding: every guest request resolves device → hotel → room → active stay on
       the server. Rejected if the device is disabled, revoked, reassigned or its credential fails.
       Heartbeat every 30 s updates last_seen_at ; offline after 90 s.
       Idempotency: Idempotency-Key header required on order create, payment record, tip
       confirm, checkout, pairing and adjustments. Same key + same body returns the stored
       response; same key + different body returns 409.
       Rate limiting and lockout: 5 failed PINs locks that PIN for 15 min; login and pairing
       endpoints rate-limited per IP and per account.
       Errors: clients get {code, message, request_id} ; stack traces and SQL errors stay in
       server logs only.

  Realtime events
  Clients subscribe to scoped channels after authenticating the WebSocket; every event
  carries event_id , hotel_id , occurred_at and a monotonically increasing seq so a
